# DataLineage AI — Milestone 14: Secure Test Deployment

This guide prepares a **controlled test deployment**, not a claim of production certification. The supplied Docker Compose configuration binds the app to `127.0.0.1` only; remote users cannot reach it directly. Do not expose confidential production SQL during this test.

## What is included

- A Docker image that runs the existing FastAPI application as a non-root user.
- A persistent named volume for the existing SQLite analysis and account databases.
- A single Uvicorn worker. This is intentional because the current login/signup/token rate limits are in-process and are not shared across workers or replicas.
- A container readiness check using `/ready`.
- Secret/database exclusions in `.gitignore` and `.dockerignore`.
- No automatic deployment, public exposure, paid service, or database reset.

## 1. Prerequisites

Install Docker Desktop for Windows and make sure its engine is running. Open PowerShell at the project root (the folder containing `Dockerfile` and `docker-compose.yml`).

## 2. Create the private environment file

```powershell
Copy-Item .\backend\.env.example .\backend\.env
```

Edit `backend\.env` locally. Never commit or share this file. For a controlled deployment, set at least:

- `DATALINEAGE_ENVIRONMENT=production`
- `DATALINEAGE_AUTH_ENABLED=true`
- `DATALINEAGE_AUTH_USERNAME` to a non-default administrator username
- `DATALINEAGE_AUTH_PASSWORD` to a unique password of at least 16 characters (prefer a longer password generated by a password manager)
- `DATALINEAGE_SESSION_SECRET` to a newly generated random secret with at least 32 bytes of entropy
- `DATALINEAGE_SECURE_COOKIE=true`
- `DATALINEAGE_PUBLIC_BASE_URL` to the real HTTPS URL that users will open
- `DATALINEAGE_CORS_ORIGINS` to explicit HTTPS browser origins only
- `DATALINEAGE_EMAIL_DEV_MODE=false`
- `DATALINEAGE_SMTP_HOST`, `DATALINEAGE_SMTP_PORT`, `DATALINEAGE_SMTP_FROM_EMAIL`, and the appropriate SMTP credentials/TLS settings for your provider

The production configuration intentionally fails closed unless authentication, HTTPS URL, secure cookies, explicit HTTPS CORS origins, and encrypted email delivery are configured correctly. Do not use the example placeholders as real secrets. If the provider supports an application password, use that instead of your normal account password.

Generate a random secret in PowerShell (copy the output directly into your private `.env` file; do not paste it into chat or commit it):

```powershell
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

The current `backend/.env.example` contains development-oriented defaults for local work. **Change the settings listed above before running the production-mode Compose deployment.**

## 3. Build and start the controlled test instance

From the repository root:

```powershell
docker compose config
docker compose up --build -d
docker compose ps
docker compose logs --tail 100 datalineage-ai
```

Review `docker compose config` output privately before sharing it; resolved environment values can contain secrets. Do not paste secret-bearing output into tickets or chat.

Open `http://127.0.0.1:8000/` on the same machine. This local URL is suitable only for checking the container through the local port. Since production mode requires Secure cookies and an HTTPS public base URL, login/signup flows should be tested through the configured HTTPS reverse proxy, not over plain HTTP.

## 4. HTTPS and remote testers

The Compose file deliberately does not publish the service publicly and does not configure TLS. Before inviting remote testers:

1. Choose a hosting environment and configure a trusted reverse proxy or hosting platform to terminate HTTPS.
2. Keep the application port private to the proxy/network; do not expose port 8000 directly to the internet.
3. Configure the real HTTPS public base URL and exact allowed browser origins.
4. Confirm secure cookies work over HTTPS.
5. Add platform-level request/body limits, access logs with sensitive values redacted, and network restrictions.
6. Verify email verification and password-reset delivery end to end.
7. Invite only selected testers and use synthetic or non-sensitive SQL until the deployment has received a separate security review.

Do not enable proxy-header trust broadly. If the hosting platform requires forwarded headers, configure trust only for the actual proxy addresses supported by that platform.

## 5. Verify health and application behavior

```powershell
Invoke-RestMethod http://127.0.0.1:8000/health
Invoke-RestMethod http://127.0.0.1:8000/ready
docker compose ps
```

`/health` is a liveness check. `/ready` checks whether the analysis-history SQLite store can be accessed. Neither endpoint should be treated as a complete security or functional test.

After logging in through the correct HTTPS URL, verify:
- unauthenticated API requests receive `401`;
- authenticated SQL analysis and report downloads work;
- an invalid or oversized upload is rejected safely;
- email verification and password reset work with real SMTP delivery;
- saved analysis history survives a container restart.

Run the full automated suite on the same source revision before and after deployment. From Windows PowerShell:

```powershell
cd .\backend
python -m pip install -r requirements.txt
python -m pytest -v
```

## 6. Database persistence and backups

The Compose named volume `datalineage_data` stores both `analysis_runs.sqlite3` and `users.sqlite3` at `/app/backend/data`. The app must be stopped or the SQLite files must be backed up using a SQLite-consistent backup method before copying database files. Do not delete the named volume when updating the image.

Stop/start without deleting data:

```powershell
docker compose stop
docker compose up -d
```

A basic offline backup procedure:

```powershell
docker compose stop
docker volume ls
```

Find the volume whose name ends in `_datalineage_data`, then substitute that exact name for `ACTUAL_VOLUME_NAME` below:

```powershell
docker run --rm -v "ACTUAL_VOLUME_NAME:/data" -v "${PWD}:/backup" alpine sh -c "tar czf /backup/datalineage-data-backup.tgz -C /data ."
docker compose start
```

Store backups encrypted, restrict access, and test restore procedures before relying on them. Never upload a database backup publicly: the user database contains password hashes and authentication tokens, and the analysis database contains saved analysis output.

## 7. Updates and rollback

Before updating, create and verify a backup. Keep the previous image or source revision available for rollback. Rebuild and restart with:

```powershell
docker compose up --build -d
docker compose ps
docker compose logs --tail 100 datalineage-ai
```

No schema reset or database deletion should be part of an ordinary update. Back up the volume before any migration.

## Known limitations and remaining risks

- This is a controlled test deployment foundation, not a penetration-test result, compliance certification, or guarantee of production readiness.
- Rate limits are in-process; do not increase worker count or replicas without implementing a shared rate-limit store and coordinated controls.
- SQLite is suitable for a small controlled pilot but may limit concurrent writes and horizontal scaling. Keep persistent storage and backups; assess a managed database before broader use.
- The current app serves a frontend with inline scripts/styles, so the existing Content Security Policy permits inline code. A stricter CSP would require refactoring the frontend.
- HTTPS termination, DNS, SMTP provider setup, secret storage, monitoring, retention policies, and host-level firewall rules must be configured and verified separately.
- Authentication is not a substitute for a security review. Validate account recovery, authorization boundaries, session revocation, and cross-account access with real test accounts before handling customer data.
- Do not use real customer SQL or sensitive data until access controls, data handling, backups, retention, and the deployment environment have been reviewed.

## Rollback / stop

To stop the service without deleting persistent data:

```powershell
docker compose down
```

Do **not** use `docker compose down -v` unless you explicitly intend to delete the persistent database volume.

## Milestone 20 SaaS configuration

Keep the analysis, user, and SaaS SQLite databases on persistent storage and back them up together. Set `DATALINEAGE_SAAS_DB_PATH` explicitly in container deployments. Organization-specific GitHub connections require `DATALINEAGE_GITHUB_CREDENTIAL_KEY`, a Fernet key generated with `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`. Store this key outside the repository in a secrets manager. Do not deploy without HTTPS, secure cookies, strong session secrets, email delivery, and a shared rate limiter at the gateway if running multiple instances.

No payment provider is configured by this milestone. Subscription plan changes and trials are internal state changes only.
